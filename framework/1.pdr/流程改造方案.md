# 流程改造方案（对齐实际访谈流程）

> 依据：用户 2026-11-12 口述的真实流程。本文是改造基准，实施后同步更新 [选拔系统PRD.md](选拔系统PRD.md)。
> 与旧版的差异见文末「变更清单」。

---

## 一、实际流程（五阶段）

| 阶段 | 时间 | 谁做什么 | 系统要存什么 |
| --- | --- | --- | --- |
| **1 讲座** | 10/29 下午 | 学院发公告通知；**可选**签到签退 | 公告；签到记录（可选） |
| **2 实训室开放** | 讲座后同步开启 | 学生自学、参观、交流；**可选**线上师生答疑 | 公告；（可选）聊天记录 |
| **3 意向填报** | 11/2 | 学生填 **3 个**任意实训室的不同导师，各自选是否服从调剂 | 填报 + 3 条意向 + 两个调剂意愿 |
| **4 面试考核** | — | ① 导师**先初选**，只把一部分报名者拉进面试名单；② 面试后填评价 + 学生展示内容；③ 出三份名单：**拟录取 / 递补 / 内部调剂**；④ 内部调剂由导师**指定**目标导师，一般不二次面试、默认拟录取 | 入围记录、评分、三份名单（带排序）、调剂目标导师 |
| **5 拟录取与确认** | — | 学生收到通知后**选择**导师；确认是**暂时**的，可撤销重选；名额释放后该导师**递补第一名**收到通知被录取；导师名额空出后可递补或等下一轮 | 意向状态、确认/释放记录 |
| **6 分轮补录** | — | 未录取学生重新填报，同样走"入围 → 面试 → 名单 → 选择" | 新一轮数据 |
| **7 统筹调剂** | — | 兜底安排仍未着落的学生 | 调剂记录 |
| **8 公示与入组** | — | 公示 1 天，无异议后正式入组 | 公示状态 |

### 与旧实现的关键差异

| 环节 | 实际流程 | 旧实现 |
| --- | --- | --- |
| 面试资格 | 导师**先筛人**，不是所有志愿都有面试机会 | 全员可评 |
| 内部调剂 | 导师**指定**调到哪位老师 | 导师只圈候选，管理员统筹 |
| 名单排序 | 拟录取/递补都要排序 | 只有递补有顺位 |
| 录取方式 | 默认人工挑选 + 给拟录取排顺位；"自动录取"接口已在 2026-11-16 移除，暂未实现 | 只能人工 |
| 学生确认 | **暂时确认、可改**，释放后递补 | 一次性终局，确认即放弃其他 |
| 学生展示 | 导师录"学生展示的自身相关" | 只有四维评分 + 评语 |

## 二、数据模型变更

### 1. 新增 `interview_invite`（面试入围）

```sql
CREATE TABLE interview_invite (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  round_no    INT             NOT NULL,
  lab_id      BIGINT UNSIGNED NOT NULL,
  mentor_id   BIGINT UNSIGNED NOT NULL COMMENT '发出邀请的导师',
  student_id  BIGINT UNSIGNED NOT NULL,
  created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_invite (round_no, mentor_id, student_id),
  KEY idx_invite_lab (round_no, lab_id, student_id)
)
```

- **入围是导师级动作**：A 导师可以把学生拉进面试名单
- **面试名单是实训室级**：本室任一导师拉进来的人，都出现在本室统一面试名单里（去重）
- 未入围的人：不出现在导师的面试评分页，也不能被写入三份名单

### 2. `offer` 增加字段

| 字段 | 说明 |
| --- | --- |
| `target_mentor_id` | 仅 `type='ADJUST_CANDIDATE'` 用：导师指定的接收方导师 |
| `rank_no` | 已有。现在 **拟录取也要排序**（原先只有递补用） |

### 3. `interview_score` 增加字段

| 字段 | 说明 |
| --- | --- |
| `showcase` | 学生面试时展示的内容（项目、作品、经历），导师录入 |

### 4. 名单排序

- 拟录取：`rank_no` = 1..n（1 为第一顺位）
- 递补：`rank_no` = 1..m（独立编号，从 1 开始）
- 内部调剂：`rank_no` = 1..k

> 排序在 `POST /teacher/lists` 里随名单一起提交（数组顺序即顺位）。

## 三、接口变更

### 面试入围

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/teacher/invites` | 把学生拉进面试名单 `{round, studentIds:[]}` |
| `DELETE` | `/api/teacher/invites/{studentId}?round=` | 取消入围 |
| `GET` | `/api/teacher/applicants` | 返回增加 `invited`（本室是否已入围）、`invitedByMe` |
| `GET` | `/api/teacher/interview-list` | 本室面试名单（入围者的并集，含评分状态） |

### 名单排序（原"自动录取"）

> **2026-11-16 更新：`POST /api/teacher/lists/auto` 已被移除，当前版本没有"自动录取"。**
> 导师在「名单管理」里按面试评分自己勾拟录取 / 递补，并用 ↑↓ 调整顺位；
> 提交时系统按名单写入 `offer.rank_no`，后续递补按顺位上位。
> 如需恢复"按评分自动录满名额"，参考 `更新记录.md` 2026-11-16 那节。

| 能力 | 现状 |
| --- | --- |
| 拟录取 / 递补排序 | ✅ `offer.rank_no`，导师可 ↑↓ 调整 |
| 按评分自动录满 | ❌ 未实现（接口已移除） |

### 内部调剂（导师指定）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/teacher/adjust-inbox` | 别人指定给我的调剂学生 |
| `POST` | `/api/teacher/adjust-inbox/{offerId}/accept` | 接收 → 变成我的拟录取（占我的名额） |
| `POST` | `/api/teacher/adjust-inbox/{offerId}/reject` | 拒绝 → 退回发起人 |

### 阶段 5 选课式

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/student/offers/{id}/confirm` | 确认（**暂时**）；若已有其他确认，自动释放那一个 |
| `POST` | `/api/student/offers/{id}/release` | 撤销确认 → 该意向回到"待确认"，**同时触发该导师递补第一名被录取** |

**核心规则**

1. 同一学生同一轮**最多一个** `CONFIRMED`
2. 确认时校验目标导师 `已确认人数 < 名额`，满了报 `2003`
3. 释放时：把名额还回去，并把该导师 **递补 rank 最小的 ISSUED 记录** 提升为拟录取（状态 `ISSUED`，学生会在通知里看到）
4. 确认**不再**把其他意向置为 `DECLINED`（旧逻辑），改为只释放自己那条 → 学生可以随时改主意

## 六、安置检查（确保最后每个人都有实训室）

最后一次调剂之后，剩下的未安置学生在「统筹调剂」顶部逐个「指定安置」，再由系统校验：

| 步骤 | 规则 |
| --- | --- |
| 1. 指定安置 | 管理员选学生 + 导师 + 必填原因，直接置 CONFIRMED，备注"学院统筹安置：原因" |
| 2. 调剂优先级 | ① 室内调剂（须服从）→ ② 跨室调剂（须服从），后端强制校验，不可跳级；只有「在本室还有空位」的学生会卡住 ②，报过的实训室全满的学生直接进 ②（否则会死锁） |
| 3. 安置校验 | 每个已填报学生**恰好一个** CONFIRMED；导师已确认人数 ≤ 名额 |

**硬约束**：校验不通过时，`POST /admin/publicity/publish` 会直接拒绝，并报出"还有 N 人没有实训室"。

**接口**：
- `GET  /api/admin/placement/gaps?round=` 缺口清单（未安置名单、各导师剩余名额、名额是否够用）
- `GET  /api/admin/placement/verify?round=` 安置校验
- `POST /api/admin/placement/assign` 指定安置，body `{round, studentId, mentorId, reason}`

**页面**：管理后台 →「统筹调剂」顶部「安置检查」卡片。

### 跨室转组（已录取学生对去向不满意）

原来由管理员在③里逐条"约谈安置"的那块，改成学生自己发起：

| 步骤 | 谁操作 | 规则 |
| --- | --- | --- |
| 1. 提交申请 | 已确认录取的学生 | 仅阶段 7；选**其他实训室 + 该室导师** + 必填理由（≤200 字）；同一时间只能有一条待处理 |
| 2. 约谈后处理 | 目标导师 | 调剂收件箱里「接收」或「拒绝」；可填约谈记录 |
| 3. 接收效果 | 系统 | 旧的 `offer` 置 `VOID`，新插一条 `ADMITTED/CONFIRMED` 占目标导师名额，学生收到站内通知 |
| 4. 拒绝效果 | 系统 | 学生保留原去向，看到拒绝原因 |

**接口**：
- `GET    /api/student/transfers?round=`
- `POST   /api/student/transfers` body `{round, targetLabId, targetMentorId, reason}`
- `DELETE /api/student/transfers/{id}`
- `GET    /api/teacher/transfer-inbox?round=`
- `POST   /api/teacher/transfer-inbox/{id}/accept` body `{interviewNote}`
- `POST   /api/teacher/transfer-inbox/{id}/reject` body `{reason, interviewNote}`

**页面**：学生端 →「我的选拔」→ 已确认那条后面的「申请跨室转组」；导师端 →「名单管理」页的「学生转组申请（约谈后处理）」卡片。

> 旧导师腾出的名额不自动递补：阶段 7 已经没有"学生确认"环节，递补上来的意向会卡住，留给管理员在安置检查里统一处理。
### 安置之后：结果怎么"被看见"

统筹安置不是偷偷改数据库，有两条可见路径：

| 路径 | 谁操作 | 留痕 |
| --- | --- | --- |
| **指定安置**（约谈后同意去某个导师） | 管理员选学生+导师+**必填原因** | `offer.remark` = "学院统筹安置：<原因>"；操作日志记操作人、时间、原因 |
| 改派 | 管理员 | 原确认记录置 EXPIRED，新记录 CONFIRMED，日志留痕 |

学生端「我的选拔」：被安置的那条会显示橙色「学院统筹」标签 + 原因原文。

公示名单：被安置学生和其它人一样正常列出（不额外公开贴"统筹"标签，避免公开标签化），
公示前必须先通过安置校验，否则发布被拒。

接口：`POST /api/admin/placement/assign`，body `{round, studentId, mentorId, reason}`，reason 必填。
时间约束：与 ①② 一致，只在「统筹调剂录取」环节（第 7 步）开放时间内可用；还在填报/初选/拟录取/补录时，后端直接返回"当前不在「统筹调剂录取」的开放时间内"。

### 安置与公示的轮次规则（跨轮判定）

| 场景 | 规则 |
| --- | --- |
| **只有第 1 轮**（没开补录） | 第 1 轮就是最终轮 → 必须全员有着落才能公示 |
| **开了第 2 轮** | 第 1 轮不再是最终轮 → 允许还剩人在等补录，此时可以公示第 1 轮的结果 |
| **第 2 轮把某人录取了** | 第 1 轮的"缺失"自动清零（跨轮判定：本轮或之后任一轮有 CONFIRMED 即算有着落） |
| **最终轮** | 必须全员有着落 + 无重复 + 无超录，否则公示被拒 |

- "最终轮" = 状态为 `OPEN` 或 `CLOSED` 的最大轮次（`PLANNING` 的不算）
- 校验接口会返回 `finalRound` 和 `lastRound`，前端据此提示
- 公示一旦发布，该轮的去向锁定：学生不能确认/撤销/申请转组，管理员不能再安置/改派，导师也不能再处理转组
